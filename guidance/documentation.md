- **Make every XML doc comment claim only what the member and its type actually do: no validation the default implementation skips, no values a method doesn't copy or set, and no claim about how data is represented or how long it lives that other members or callers contradict.** Callers, and authors of custom implementations, rely on documented checks and representations. - **Make `<exception>` and `<see cref>` entries name the real types: one `<exception cref>` per exception type actually thrown, saying when it is thrown, with text that agrees with the cref. - **Don't ask for a decision record to be edited in a way its repository's convention rules out. - **In production code, give every type or member you add, or whose signature or behaviour you change, a `///` comment with a substantive `<summary>`, plus `<param>`, `<returns>` and `<remarks>` where they help. This includes private and private static helpers, where `<returns>` says what a bool result means, and members of benchmark projects. Use `/// <inheritdoc />` for interface implementations, update the comment when you rename or change the member, and don't add comments to code you aren't otherwise changing.** Docs ship to consumers and must match the code, a package build fails on undocumented public members (CS1591), and a helper's lookup or return behaviour should be documented where it is defined. *Check:* Look for added or changed members, private helpers and `[GlobalSetup]`/`[Benchmark]` methods included, that have no `///`, only a `//` comment, an empty or name-restating summary, or stale docs. - **Give every parameter of a documented method a `<param>` tag, including a `CancellationToken`. - **When a method returns or `out`s a rented buffer lease together with a span or memory view over it, its `///` docs state that the caller owns and must dispose the lease, and that the view is read-only and valid only until the lease is disposed. - **When a property on a context or pipeline type shared among extension contributors stays publicly settable, its doc comment says who sets it and who reads it.** Otherwise any contributor might overwrite a value that an earlier contributor planned against. *Check:* Look for public settable properties on context or pipeline types whose summary doesn't name their writer and reader. <sub>Identity outcomes of #592</sub>
- **Start a property's summary with 'Gets or sets' only when it has a `set` accessor. - **Keep `///` text to the contract a consumer can use. - **Don't report a pre-existing convention violation on a line that a mechanical bulk edit, such as renumbering or renaming references, only rewrote. - **Write comments, XML docs and help text in the timeless present about the code as it is: no 'now', 'new', 'no longer', 'previously', 'used to' or 'renamed', no history of the bug that led to the code, and no name of a removed or renamed member.** Change narration becomes wrong once the change merges and makes a reader who never saw the earlier version guess what it was. - **Put the reason for a non-obvious choice in a comment where the choice is made, not only in the PR description.
