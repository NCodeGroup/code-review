- **Never commit secrets or credentials (connection strings, passwords, API keys, tokens, signing keys) in source or in committed configuration files. Load them from a secure configuration source.** A committed secret is a leaked secret, whether or not the code uses it. *Check:* Look for credential literals in code, appsettings*.json, *.config files or chart values. <sub>NCodeGroup maintainer: principal-engineer-review; Identity ADR-1235</sub>
- **Don't add an option that turns off or relaxes a security control (CSRF checks, cookie attributes, callback binding, return-URL or proxy allow-lists, signature or key-role checks). A setting may only choose equal or stronger behavior, and every library default must be safe.** Secure by default with no off switch means a misconfiguration can't open a gap. A default may be permissive only where the caller's policy is unknown, and never in a way that weakens security. *Check:* Look for new boolean or enum options such as `DisableCsrf`, `SameSite=None`, wildcard allow-lists, or defaults that accept unsigned tokens, decrypt with a verification key, or skip a check the caller asked for. <sub>Identity docs/backend-for-frontend.md; Identity ADR-1154</sub>
- **In production code, bind each options type from its whole configuration section with `BinderOptions.ErrorOnUnknownConfiguration = true` at every depth, and register it with `ValidateOnStart()`. Never read single keys with `configuration["Section:Key"]`, `section[key]` or `GetValue`, even for a section read before dependency injection is set up. Bind such a section strictly to a small options type instead.** The binder silently drops keys that map to no property, so a misspelled or stale key leaves the host running on defaults (wrong port, no TLS, in-memory store). Strict binding with start-up validation stops the host with an error that names the key. *Check:* Look for `Bind`, `Configure<T>(section)` or `AddOptions<T>().Bind(...)` calls without `ErrorOnUnknownConfiguration`, options registrations without `ValidateOnStart`, and per-key indexer or `GetValue` reads of configuration. *Note:* Options that a library configures only through an `Action<TOptions>` callback, and never binds from configuration, are exempt (see the rule on callback-configured options). A Blazor WebAssembly host runs no start-up validation (see the WebAssembly rule). <sub>Identity ADR-1137; Identity ADR-1062; Identity ADR-1290; Identity ADR-1139; Identity ADR-1223; Identity ADR-1510; Identity ADR-1474; Identity csharp.instructions.md; Identity csharp-production.instructions.md; Identity docs/backend-for-frontend.md; Identity outcomes of #819</sub>
- **Give each configuration section one owner. The owner binds all of the section's subsections and rejects any subsection it doesn't recognize, listing the ones it does. Packages and extensions bind their own sections and never add keys under a section that another component owns, including a section owned by a third-party library such as YARP's `ReverseProxy`.** With one owner, a misplaced subsection is caught instead of ignored. Strictly binding another library's section would refuse that library's own keys. *Check:* Look for a package that binds a subsection of a section owned elsewhere, options bound to `ReverseProxy` or another library's conventional section, or a section owner that doesn't reject unknown subsections. *Note:* Don't ask a host to reject keys in the `ReverseProxy` section, because YARP reads its routes from it.
