- **Enforce each security or validation rule in one shared implementation that every entry point calls. Examples: one key-import policy for every way a key arrives, one JWT validation core configured per token kind, JWT lifetime caps in the shared lifetime requirement, resource-indicator narrowing at the shared audience-resolution step, and pushed authorization requests validated by the authorization endpoint's own validation. Do not copy the checks into individual handlers, grants or endpoints, and do not state the same rule twice (for example as a setting ceiling and again as a separate requirement).** Copies of security checks drift apart. Entry points that checked keys differently already let invalid or private keys through, and a new path that skips the shared step loses the check entirely. *Check:* Look for signature, algorithm, issuer, audience, exp/iat/nbf, resource or key validation written inline in a handler, endpoint, grant or resolver instead of calling the shared validator. Also look for a new token or key path that bypasses the shared step, and for new requirement classes that re-check a constraint a setting or profile ceiling already expresses. <sub>Identity ADR-0161; Identity ADR-0301; Identity ADR-0124; Identity ADR-0078; Identity ADR-0089; Identity ADR-0158; Identity ADR-0225</sub>
- **When several entry points perform the same protocol operation, send them all through one shared pipeline or service. Examples: every sign-out path runs the shared end-session command, device verification reuses the authorization endpoint's authentication and consent path, every token delivery mode builds its response with one shared composer, and every grant revocation goes through the central service that owns the re-read-and-retry loop.** Separate copies of one operation end up behaving differently: sessions are not revoked, tokens differ between delivery modes, or a revocation that should succeed returns 500 or 412. *Check:* Look for a new logout, consent, token-response or revocation path that has its own cookie clearing, revocation, retry loop or token construction instead of calling the shared command or service. <sub>Identity ADR-0074; Identity ADR-0059; Identity ADR-0085; Identity ADR-0215</sub>
- **Do not hardcode or copy the default logic of a behavior the host can configure (for example `sub ?? nameidentifier`), and do not put it in a public static helper. Call the single configured seam so a host override applies everywhere.** A copy shares the default but skips the override, so a host's customization works on one surface and is silently ignored on another. *Check:* Look for inline claim lookups or static helper calls that work out a value which already has a configurable seam, instead of calling the context or environment method. <sub>Identity ADR-0053</sub>
- **Model a notification that only observes an operation (audit, log, metric, notify) as a fault-isolated event published through the event publisher, not as a void NCode.Mediator `ICommand`. Publish it only as the last step, after the operation has finished. Use a mediator command only when a handler can reject the operation, change state the caller reads, or return a value the caller uses.** On the mediator, the first handler that throws stops the others and fails the request. Events observe outcomes and must never decide them. *Check:* Look for void `ICommand` types or handlers that only log, audit or notify. Look for `PublishAsync` calls placed before the main operation finishes, or whose result decides whether the operation continues. Look for event handlers that try to reject an operation or change data the caller uses. <sub>Identity ADR-0047</sub>
- **Services must never call command handlers directly. They reach handlers only by sending a command through `IMediator`, while handlers may call services.** Calling a handler directly hard-wires one participant. The sender must not know who handles the command. *Check:* Flag services or endpoints that inject or construct a concrete `ICommandHandler<T>` or `ICommandResponseHandler<T, R>` and call it instead of `mediator.SendAsync`. <sub>Identity ADR-0001</sub>
- **Outside the store implementation, catch the store-neutral `StoreConcurrencyException`, never Entity Framework's `DbUpdateConcurrencyException`.** Catching the EF type ties protocol and service layers to one store technology, and any other store would have to throw EF's type to be handled. *Check:* Look for `catch (DbUpdateConcurrencyException` in projects other than the EF store, or for EF package references added only to catch that type. <sub>Identity ADR-0208</sub>
- **Map a cross-cutting exception, such as a store concurrency exception, to an HTTP response in one endpoint filter on the shared or root route group. Do not use a try/catch in each handler.** Catches in each handler drift apart, and a handler added later forgets the catch and returns 500. *Check:* Look for handlers that catch a domain exception and build the error response themselves when a group filter exists, and for endpoints registered outside the group that carries the filter. <sub>Identity ADR-0214; Identity ADR-0245</sub>
- **Do not design features that need sticky sessions or need a follow-up request to reach the same replica.** Any replica must be able to serve any request. Sticky routing breaks redundancy and replica replacement. *Check:* Flag state kept in process memory between related requests (for example between authorize and callback), or session-affinity configuration. <sub>Identity ADR-0134</sub>
- **When a result is needed in several places (a merged effective setting, a condition both logged by a background job and reported by an API, a preview of a resolved value), compute it in one injectable service that every caller uses. Do not repeat it by hand or put it in a static helper.** Copies of the computation read different sources and disagree, so a preview or report misleads operators. A static helper cannot be replaced by the host and cannot take dependencies. *Check:* Look for preview, diagnostic, hosted-service or API code that rebuilds merge, resolution or evaluation logic instead of calling the service the runtime pipeline uses. Also look for new static helpers holding logic a host should be able to override. <sub>Identity ADR-0040; Identity ADR-0204; Identity ADR-0233</sub>
- **Map claims between JSON and `Claim` (in both directions) through the single shared JWT claim mapper and claims-identity factory. - **Handle key material through the shared pipelines. - **Use an NCode.Mediator command only for a deliberate request-pipeline seam: the sender must not know the handlers, consumers need to add, reorder or override participants, priority/pre/post/exception semantics are needed, or many contributors change shared state.
