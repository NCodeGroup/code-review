- **Do not skip, disable, delete or weaken existing tests or assertions to make a change pass. Fix the code, or update the test to match the new correct behavior and say why.** Skipped or weakened tests hide broken behavior while the checks stay green. *Check:* Look for newly added Skip attributes, tests that are commented out or deleted, removed assertions, or loosened expectations (an exact check replaced by NotNull or a wider range) with no behavior change that justifies them. <sub>Identity .claude/commands/review-plan-diff.md; Identity .github/agents/copilot-reviewer.agent.md</sub>
- **Make a negative test fail only because of the rule under test. Make the refused path otherwise viable: register a working implementation of the denied algorithm or item (including a working `none` algorithm when testing a `none` guard), and arrange any refused fallback so it would succeed. Pair each with a control test where the same path succeeds because the rule doesn't apply.** If the denied item isn't registered or the fallback can't work anyway, the refusal happens for some other reason and the test still passes with the rule removed. *Check:* Look for deny or refuse tests where the denied item is not registered, the fallback is not viable, or no permitted control test exists alongside them. <sub>Identity ADR-0282; Identity ADR-0295; Identity csharp-testing.instructions.md</sub>
- **Give a negative test input that every earlier or built-in check accepts, so only the rule under test refuses it. This includes a key size the algorithm accepts when testing curve binding, values the default rules don't already reject when testing an extension's rule, a request the old code accepted and deferred when testing a refusal moved earlier, and a seeded client registered for the exact authentication method being tested. Assert the specific error text when another check could refuse the same input with a different message.** When an earlier check, a built-in rule or a mismatched registration refuses the input, the test passes even with the rule under test removed. *Check:* Look for negative tests whose input an earlier validation step would also refuse, for example a wrong-curve key of the wrong size, standard names the defaults already reject, input the old code also refused, or a client whose token_endpoint_auth_method differs from the one used. Also look for tests that assert only failure where the message is what tells the causes apart. <sub>Identity csharp-testing.instructions.md</sub>
- **When a test seeds data that is meant to be invalid or unreadable, first assert that the system actually rejects it, then assert the downstream behavior.** Without that precondition the test can pass on data the server reads without trouble. *Check:* Look for tests that seed corrupt or incoherent data and go straight to downstream assertions, with no check that the data is rejected. <sub>Identity csharp-testing.instructions.md</sub>
- **When the code under test swallows exceptions, make the test fail through mock verification (for example `.Verifiable(Times.Never())`) or by asserting that the error logger was not called. Don't rely on a strict mock throwing.** The code swallows the strict mock's `MockException`, so the test passes whatever the code does. *Check:* Look for tests of code that catches exceptions broadly where the tests depend only on strict mocks throwing and never verify. <sub>Identity review of #420</sub>
- **Cover the edge cases and failure modes of a new or changed capability, not only the success path.** An untested branch, validation or error path is a gap the review is meant to catch. *Check:* For each new or changed branch, validation or error path in production code, confirm that some test exercises it. Flag test changes that cover only the happy path. <sub>NCodeGroup maintainer: gap-hunting-review</sub>
