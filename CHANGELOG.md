# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Shadow mode for a new reviewer or prompt: a charter with `shadow: true` in its frontmatter, or named in `CODE_REVIEW_SHADOW`, runs as usual, but its findings go only to the trace and a collapsed "Shadow findings (not posted)" section of the check run, never to synthesis, the threads, the summary or the verdict. A `prompts/<name>.shadow.md` runs beside the live prompt on the share of reviews `CODE_REVIEW_SHADOW_RATE` sets (0 by default), sampled by pull request and head, with both outputs in the trace. The evals score shadow reviewers apart from the live ones ([#53](https://github.com/NCodeGroup/code-review/issues/53)).
- `/review teach <rule>`, `/review teach F3 <rule>` and `/review teach org <rule>` turn a correction into lasting guidance: with no model call, the publish step opens an issue labelled `review-guidance`, in this repository or, for `org`, in NCodeGroup/code-review, quoting the rule as data with a link to the comment and, for `F3`, the finding's file, line and text, and replies with a link to it. It creates the label when it's missing and uses a second app token that can write only issues, so a review never asks for issues write; when the app lacks that permission the reply says so. `npm run train` copies the rules of `teach org` issues closed as completed into `training/feedback.md` before it generalizes. Writers only, top-level comments only, no forks, as for `/review` ([#45](https://github.com/NCodeGroup/code-review/issues/45)).
- `/review explain F3`, or `/review explain <link to a finding comment>`, with an optional question, answers in a top-level comment whether the finding still holds: one Sonnet agent with Read, Grep and Glob, locked down like the reviewers and capped at about $0.50, reads the latest commit again. An id means the newest review's finding; an id or link that isn't one gets a comment listing the newest review's ids. Writers only, no forks, as for `/review` ([#44](https://github.com/NCodeGroup/code-review/issues/44)).
- Reviews know which files a repository's project template owns. In a pull request that adopts or updates NCodeGroup/project-template, from an author with write access, its replaced-on-update files (`.template/`, its hooks, its generated commands, prompts, skills and agents, `CLAUDE.md` and a few more, minus `project_owned_files`) are marked template-owned for the reviewers and no longer choose reviewers or rules. Findings on them, except blockers, aren't posted as threads: the summary lists them once, with file and line, under "Belongs upstream, in NCodeGroup/project-template", on a first review and a re-review alike. An adoption or template update is still reviewed for the project's answers, merged files and own files. A new eval case replays the adoption in [#23](https://github.com/NCodeGroup/code-review/pull/23) ([#31](https://github.com/NCodeGroup/code-review/issues/31)).
- The review is acknowledged within seconds, before setup-node and `npm ci`: 👀 on a `/review` comment and the "Code review" check run in progress, "Review started at <commit>; it usually takes a few minutes", which the publish step then completes instead of posting a second one. The acknowledgement makes the review step's own decision, so a comment that isn't `/review` from a writer, a fork, or an automatic run on a commit already reviewed gets nothing. Nor does `/review explain` or `/review teach`, which answer with a comment, not the check run. Its token is minted from the app key the action already receives, used by the acknowledgement alone and revoked before the review step starts, so consuming workflows need no change ([#20](https://github.com/NCodeGroup/code-review/issues/20)).
- Evals measure precision: each posted blocker and should-fix that matches no expected concern is judged `real`, `not-real` or `unsure` by Opus reading the checkout, with verdicts cached in `evals/verdicts.json`. Each output also reports findings per case (mean, max) and the review's cost per case. `npm run eval:compare` compares two runs, marking recall differences of 2 or less as noise, and `npm run eval:confirm` adds confirmed verdicts to `cases.json` as expected or must-not-flag concerns ([#51](https://github.com/NCodeGroup/code-review/issues/51)).
- A finding whose fix is a mechanical edit of up to five lines, all of them added by the pull request, carries a GitHub suggestion block on a comment that covers those lines, so it applies with one click; any other fix stays in prose. The hidden marker on each inline comment also names its reviewers, and comments posted before still count as already posted ([#54](https://github.com/NCodeGroup/code-review/issues/54)).
- A per-review cost ceiling guards against a runaway review: $8 plus $4 for each part of the diff, overridable with `CODE_REVIEW_MAX_RUN_USD`. Reviewer calls not started once it is reached are skipped and shown as `skipped: run budget` in the check run, synthesis still runs on what was found, and the summary warns that the review is incomplete ([#50](https://github.com/NCodeGroup/code-review/issues/50)).
- A verification stage, off by default: with `CODE_REVIEW_VERIFICATION=on`, a Sonnet call with the checkout proves or refutes each merged blocker and should-fix, a file's findings at a time at up to $0.50 a call. Confirmed findings get the code path in their evidence, refuted ones are dropped and listed with the reason under "Refuted by verification" in the check run and in the trace, and ones it can't settle become questions one severity lower. The summary names the refuted findings, and verification turns a request for changes with nothing serious left into a comment, never an approval. Nits aren't verified, and the calls show as `verification` in the cost table. It stays off until the eval shows a gain, and the eval report now counts posted blockers and should-fixes and refuted findings ([#41](https://github.com/NCodeGroup/code-review/issues/41)).
- When a pull request closes, merged or not, each finding posted as a thread gets an outcome, by rules alone with no model call or model key: fixed (its line changed afterwards, or its thread is outdated and resolved), dismissed (a writer's 👎, resolved without a change, or a writer's declining reply), acknowledged (a writer's 👍 or reply) or ignored. The newest summary comment, or a final one, gets a table of finding, reviewer, severity and outcome with the pull request's state, and a hidden `<!-- ncode-review:outcomes {...} -->` marker that also holds each finding's review cost, provider and model (as many findings as fit in a comment, counting the rest). Summary comments now record their review's cost, provider and models in a hidden marker that a superseded summary keeps, along with its outcomes marker. A closed pull request gets no acknowledgement and no "Code review" check run. Callers need `closed` in their `pull_request_target` types, added with the pin bump to this release, since earlier releases would review a closed pull request; the README's caller has it, this repository's workflow gets it with that bump, and a closed run waits for a review in progress instead of cancelling it ([#47](https://github.com/NCodeGroup/code-review/issues/47)).
- A monthly report: on the 1st, the `Monthly report` workflow reads the pull requests closed in the month just ended in each NCodeGroup public repository with `.github/workflows/code-review.yml`, and opens the issue "Review report YYYY-MM" with precision per reviewer and per repository (fixed ÷ (fixed + dismissed), with acknowledged and ignored shown apart), findings per pull request, the total cost split between the Claude API and Amazon Bedrock, the cost per fixed finding, and the change in each from the previous month's report. Findings come from the outcomes marker and cost from the summary comments' review markers, from the bot's comments only. A re-run updates the month's issue instead of opening another, a manual run takes a month and a list of repositories, and it needs only the workflow's `GITHUB_TOKEN` ([#48](https://github.com/NCodeGroup/code-review/issues/48)).

### Changed

- When no provider is available (the API credits used up or the Anthropic login failed, and the Bedrock key missing or refused), the "Code review" check run completes neutral, titled "Review budget used up", with the reason, and the job no longer fails. Bedrock is asked once, with a one-token call, whether it accepts the key before the review relies on it ([#20](https://github.com/NCodeGroup/code-review/issues/20)).
- A review that fails, or a run that's cancelled, completes the "Code review" check run with the reason and a link to the run's log, instead of leaving nothing on the pull request ([#20](https://github.com/NCodeGroup/code-review/issues/20)).
- `npm run typecheck` fails on what a linter would warn about: unused locals and parameters, implicit returns, switch fall-through, missing `override`, `undefined` written into an optional property, dotted access to an index signature, unreachable code and unused labels. CI also runs the template's commit attribution check, on pull requests, merge queue entries and pushes to `main`.
- Consumers pin the action by a release's full commit SHA, with the tag in a comment, as the README now says: CodeQL's `extended` suite reports a tag pin, even an immutable release's, as an unpinned action. This repository's own workflow pins v0.3.1 that way.
- Each review posts its own summary comment, at the bottom of the conversation, and the previous summary collapses to one line that links to it, instead of the first summary being edited in place, so a `/review` or re-review shows its verdict and findings where it ran ([#21](https://github.com/NCodeGroup/code-review/issues/21)).
- Re-reviews converge. A review of a pull request the bot has reviewed before reviews only the hunks of its merge-base diff that differ from that diff at the last reviewed head, and what the author took out since, so nothing a merge of the default branch brings in is reviewed, and a head a force-push dropped gets a full review. Only `correctness` reviews them, on Sonnet, with the earlier findings and the replies in their threads, and checks each unresolved finding against the code now. It posts only blockers and should-fixes on lines changed since the last review, never nits, and its summary says "No further findings above nits" when nothing at or above should-fix is left, and never approves when the earlier review threads can't be read or no reviewer saw what changed. With verification on, what a re-review would post goes through it as a first review's blockers and should-fixes do; a should-fix it can't settle becomes a nit and isn't posted, and a re-review whose findings it refuted never approves or says it's done. The first review is unchanged. A review whose reviewers all failed records the head reviewed before it, so the next re-review covers what it missed. Two eval cases replay re-reviews of #29 and #30, one with main merged into the head ([#24](https://github.com/NCodeGroup/code-review/issues/24)).
- A review whose API credits run out partway no longer loses the reviewer that hit it: with a Bedrock key, that call reruns on Bedrock at the same tier and every later call goes straight there. The trace records both calls with their providers, and the check run and summary say "Switched to Bedrock partway: credits ran out" with the cost on each provider. A call that ends on an API error now counts as failed rather than as a run with no findings ([#49](https://github.com/NCodeGroup/code-review/issues/49)).
- A missing test is a should-fix only when the untested path is new behavior with a plausible failure a user would see and no test below it covers it. A wrapper over tested pieces, a test that would only pin current behavior, or a second test for a covered path is a nit. Eval concerns can name a `minSeverity`, and five cases from [#30](https://github.com/NCodeGroup/code-review/pull/30) check both sides ([#37](https://github.com/NCodeGroup/code-review/issues/37)).
- The inline threads read the pull request's earlier review comments through the same pager as the summary comment, up to 10,000 instead of 1,000. When a pull request has more, no threads are posted, with a warning, instead of findings already posted on comments past the limit being posted again; the check run still has every finding ([#38](https://github.com/NCodeGroup/code-review/issues/38)).
- The Release workflow fails before it tags when `CHANGELOG.md` has no dated `## [<version>] - YYYY-MM-DD` section with entries for the version, and publishes that section as the release's notes instead of generated ones. The README says why Dependabot proposed no bump of the action to consumers, every release so far being marked as a pre-release, and how to bump them meanwhile ([#33](https://github.com/NCodeGroup/code-review/issues/33)).

### Fixed

- A learned guidance rule that came only from instruction files, such as Identity's C# conventions, is tagged with the files they apply to (`` *Applies to:* `**/*.cs` ``) and reaches only reviews, and parts of a diff, that change such a file, so a C# rule no longer reaches a review of TypeScript. `npm run train` writes the tags, and `npm run train -- --retag` rewrites them without a model ([#36](https://github.com/NCodeGroup/code-review/issues/36)).
- A review no longer posts a finding that says a file the pull request changes isn't changed or isn't in the diff. Synthesis saw only the diffs of the files the reviewers' findings named, and no list of changed files, so on [#22](https://github.com/NCodeGroup/code-review/pull/22) it wrote a finding of its own saying `src/command.ts` had no changes. It now gets the list of changed files and every file's diff that fits its budget, the reviewers' and synthesis's prompts say the list is complete, and a finding that still makes such a claim in its title, problem or consequence is dropped before the finding limit applies. The summary comment says how many were dropped and how severe, the check run and the trace list them, and a verdict that rested on them is settled on the findings kept ([#32](https://github.com/NCodeGroup/code-review/issues/32)).
- A request for the earlier summary comments that fails outright, such as on a DNS failure or a reset connection, no longer fails the review step: the run reviews the pull request again, as it does when GitHub refuses the request ([#39](https://github.com/NCodeGroup/code-review/issues/39)).
- `tools/Enable-CodeReview.ps1 -SkipBedrock` skips only prompting for and setting the Bedrock key: the opted-in repositories still get access to the existing `AWS_BEARER_TOKEN_BEDROCK` secret, instead of failing every review once the organization's API credits run out. `-Repo` takes a comma-separated list as one value, as `pwsh -File` passes it, and `-Repo a, b` there fails before any change instead of binding `b` to another parameter. The help says which changes need the `admin:org` scope. A failure to read an organization secret, other than its not existing, stops the script instead of counting as a missing secret, and a failed grant or `secret set` shows gh's exit code ([#34](https://github.com/NCodeGroup/code-review/issues/34)).
- The `data-model` reviewer joins every review that changes a `Migrations/` folder or a `.sql` file. The floor matched one pattern against all changed paths joined together, so a `.sql` file counted only when it was the last path and a root `Migrations/` folder only when it was the first; any other order relied on the selection call. Found by CodeQL's extended suite (`js/regex/missing-regexp-anchor`).
- `npm run train` reads a saved extraction directly instead of checking that it exists first, so the file can't change between the check and the read (`js/file-system-race`).

## [0.3.1] - 2026-10-31

### Changed

- Releases are immutable from this one on: GitHub refuses any change to a published release's tag or assets. The engine is the same as v0.3.0's.

## [0.3.0] - 2026-10-31

### Changed

- The engine fetches the pull request's head itself, at the exact commit the event or the API named, once it has decided to review, so a calling workflow no longer checks out the pull request's code and CodeQL no longer reports it. Git runs without configuration, hooks or a credential helper, and the token goes through the environment. A workflow that still checks the head out into `pr` is accepted when it is at that commit ([#19](https://github.com/NCodeGroup/code-review/pull/19)).
- A fetch that takes longer than three minutes ends with its own error, and the engine refuses a pull request from a fork for an automatic review as well as for `/review` ([#22](https://github.com/NCodeGroup/code-review/pull/22)).
- The repository adopts NCodeGroup/project-template v0.41.1: the plan-then-execute workflow, `AGENTS.md` with its Landing policy, and the commit attribution check ([#23](https://github.com/NCodeGroup/code-review/pull/23)).

## [0.2.1] - 2026-10-30

### Added

- An infrastructure reviewer for OpenTofu and Terraform changes, `.tf`, `.tofu` and `.hcl` files reviewed as code, and repository rules read from instruction files that have no legend ([#17](https://github.com/NCodeGroup/code-review/pull/17)).

## [0.2.0] - 2026-10-30

### Added

- Rule checks: each batch of repository rules is checked against the change by its own reviewer, on by default (`CODE_REVIEW_RULE_CHECKS=off` turns them off).
- Evals run with held-out guidance, so a case's own review comments never train the rules it is judged by ([#16](https://github.com/NCodeGroup/code-review/pull/16)).

## [0.1.0] - 2026-10-30

### Added

- The first release: a GitHub composite action that reviews a pull request with reviewers on the Claude Agent SDK and posts the findings as the "Code review" check run, a summary comment and inline threads.
