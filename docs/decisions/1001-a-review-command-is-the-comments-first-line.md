# 1001. A /review command is the comment's first line, and only a plain one can cancel a review

- **Status:** Accepted
- **Date:** 2026-11-02
- **Deciders:** Marcin Polewski

## Context

The workflow starts the `review` job, in the pull request's `cancel-in-progress` group, for any comment that starts
with `/review`. The engine's `parseCommand` accepts a plain review only when the whole comment is `/review`. A
`/review` followed by a footer therefore joins the group, cancels the review in progress, and is then rejected as not a
command, so the pull request ends with no review ([#172](https://github.com/NCodeGroup/code-review/issues/172)).

Agents that post a comment for someone add an attribution footer, such as a `---` line and `_Generated by …_`, so the
shape is common.

## Decision

A command is the comment's first line, and only a comment whose first line is exactly `/review` can cancel a review.

- When the first line, trimmed, is `/review`, the comment is a plain review, whatever follows it. `/review please` is
  not one.
- Everything from the first Markdown thematic-break line (`---`, `***`, `___`, three or more of one character) is
  dropped before parsing, so an explain question or a taught rule never carries a footer.
- `/review`, `explain` and `teach` match in any case, because the workflow's expressions compare case-insensitively.
- The `review` job's concurrency group is the pull request's only for a comment whose body is `/review` or starts with
  `/review` and a newline. Every other comment the `if:` admits gets the group `command-<comment id>`.
- A plain `/review` with trailing spaces passes the `if:` and the engine but not the group, so it runs in a group of its
  own. It can run beside another review, never cancel one.

## Options considered

1. A pre-check job the review job `needs:`. It is exact, but it delays the acknowledgement on every `/review` and adds
   a second pinned action to every caller.
2. The first-line rule alone. It fixes the footer, but `/review please` still cancels a review and then does nothing.
3. A 😕 reaction on an ignored comment. It gives feedback only, and it needs the app token for comments that are not
   commands, which widens when a token is minted.

The first-line rule combined with the narrowed group wins: no extra job, and a comment the engine does not act on can
not cancel a review.

## Consequences

- Footers and signatures work, and a `/review` with text below it is a review.
- A `---` line in an explain question or a taught rule ends it.
- A plain `/review` with trailing spaces runs in a group of its own.
- Callers copy the `group:` line into their own `code-review.yml`.
- A comment that is ignored gets no reply; saying why is a follow-up.
